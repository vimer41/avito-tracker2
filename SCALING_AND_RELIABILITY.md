# Масштабирование и надёжность мониторинга (Avito Radar 300)

## Ключевые архитектурные решения

1. **Тарифные интервалы сканирования (20/30/40 с) и честная общая задержка**
   - Источник — канонический нормализованный URL (`AvitoParser.normalize_url`) с сохранением города, категории, поискового запроса, фильтра цены, локального приоритета (`localPriority`), радиуса (`searchRadius`) и флага поиска только в названиях (`bt=1`). Трекинговые параметры, фрагмент и номер страницы удаляются; сортировка принудительно `s=104` (по дате).
   - Целевой интервал сканирования уникального URL определяется самым быстрым активным тарифом среди подписчиков этой ссылки: **Полный / Триал / Admin = 20 с**, **Средний = 30 с**, **Базовый = 40 с** (пропорционально растягивается при нехватке прокси).
   - При наличии на одной ссылке пользователей с разными тарифами для более медленных тарифов применяется `tariff_hold = tariff_interval(tariff) - fastest_interval` (+10 с / +20 с), чтобы более дешёвые планы не ехали на скорости «Полного».
   - Выбор следующего готового источника выполняется за `O(log N)` через `heapq` с ленивой инвалидацией генераций (`scan_planner.py`).
   - Если первая страница каталога не изменила верхние 3 объявления (`last_top_ids`) и все подписанные радары уже откалиброваны (`initialized_at IS NOT NULL`), выполняется **fast-skip**: страница 2 и fanout в БД пропускаются.

2. **Тарифная дифференциация на этапе доставки, SQLite FSM и догон после паузы**
   - Состояние диалогов (FSM) хранится персистентно в SQLite (`fsm_storage.py` / таблица `fsm_states`) и переживает перезапуск/деплой.
   - Доступ к доставке в группу/канал (`handlers/group_delivery.py`) открыт только для оплаченных/активных пользователей на тарифах из `GROUP_DELIVERY_PLANS` (триалы с `is_allowed=0` исключены).
   - **Догон после подтверждённого простоя (`🕒 найдено после паузы`)**: если источник не обрабатывался дольше `max_age_minutes` (из-за рестарта, деплоя или сетевой паузы), подписчики **PRO / Admin** получают до **10 самых свежих** (отсортированных по времени публикации) пропущенных объявлений моложе **30 минут** (до 3 страниц каталога) с пометкой `🕒 найдено после паузы`. Остальные лоты из окна простоя массово помечаются в `seen_items` без спама в чат.
   - Функциональность повторных уведомлений о снижении цены (**Price Drop Alert**) полностью отключена и удалена из пайплайна и карточек настроек; колонки БД сохранены для обратной совместимости.

3. **Пул статических прокси и асинхронный HTTP-контур (`proxy_pool.py`, `parser.py`)**
   - Прокси задаются через админку (`/proxy` → таблица `bot_settings.proxy_urls`), файл `PROXY_POOL_FILE` (`proxies.txt`) или одиночный `PROXY_URL` из `.env`.
   - Каждый прокси имеет собственный `curl_cffi.requests.AsyncSession(max_clients=1)`, изолированный cookie-файл (`data/cookies/cookies_<proxy_id>.json`), собственный лимитер скорости (`PROXY_RATE_LIMIT = 1.0 req/s`, `PROXY_MAX_IN_FLIGHT = 1`) и потокобезопасный независимый карантин (`healthy` / `degraded` / `quarantined` / `half_open`).
   - При блокировке или ошибке транспорта на одном прокси задача немедленно пробует **второй здоровый прокси** (`SCAN_PROXY_ATTEMPTS = 3`) без ухода всего источника в backoff; при настроенном пуле прокси fallback на прямой IP сервера и утечка прямых загрузок изображений запрещены (`ALLOW_DIRECT_AVITO=0`).
   - Антибот (QRATOR / PoW / GeeTest) выполняется в выделенных subprocess-воркерах (`CHALLENGE_WORKERS=3` по умолчанию) без блокировки event loop.

4. **Разделение HTTP-сбора и DB Fanout (`monitoring.py`, `database.py`)**
   - Как только HTTP-сбор источника завершён, прокси немедленно освобождается, а результат передаётся через ограниченную очередь (`fanout_queue`) пулу `fanout_workers`.
   - Долгоживущий пул SQLite (`1 writer` под `asyncio.Lock` + `DB_READ_POOL_SIZE` reader-соединения в WAL-режиме) выполняет пакетное чтение `seen_items` и одну групповую транзакцию `enqueue_group_events` на весь URL.

5. **Строгая пользовательская дедупликация и высокоскоростной Telegram Outbox**
   - Уникальность доставки гарантируется на уровне **`(user_id, item_id)`** в таблице `notification_dedupe`. Один и тот же лот никогда не отправляется одному пользователю дважды, даже если совпали несколько его радаров.
   - Если до момента захвата события воркером лот совпал с несколькими радарами пользователя, их названия агрегируются в одно сообщение (`📡 Радары: «Радар 1», «Радар 2»`).
   - `OUTBOX_WORKERS` (`8` воркеров) забирают события по `(priority, deliver_at, id)` с глобальным лимитером **25 вызовов Bot API/с**, пер-чат лимитером **1 вызов/с** на `user_id` и отдельным лимитером для зеркалирования в группу (**3.1 с** на `chat_id`).

## Стартовая конфигурация (2 прокси на текущем VPS) и масштабирование до 300 URL

На стартовом VPS (1 vCPU, 600 МБ RAM, 2 статических прокси в `proxies.txt`) система работает сразу:
- при малом числе уникальных URL (до 15–20) выдерживается целевой интервал **15–20 с**;
- при большем числе URL и всего 2 прокси планировщик автоматически включает честный режим `degraded` (плавно расширяя интервал до `SCAN_MAX_INTERVAL=120 с` без падений и без вечного бэклога), а в `/stats` показывает точный дефицит прокси.

### Таблица необходимого числа прокси и воркеров (интервал 15–20 с)

Расчёт выполнен для `PROXY_RATE_LIMIT = 1.0 req/s`, коэффициента использования бюджета `0.8` (20% резерв на джиттер и повторы) и средней стоимости скана `req_per_scan_p95 = 1.3` HTTP-запроса:

## Операционное управление и диагностика

- **`/stats`** (только администратор) — выводит сводку за 15 и 60 минут:
  - активные и здоровые прокси, число уникальных URL, режим ёмкости (`normal` / `degraded`), дефицит прокси;
  - перцентили `p50` / `p95` / `p99` для цикла опроса (`revisit`), `due_lag`, HTTP-задержки, `t_pub -> t_seen`, `t_seen -> t_queued`, `deliver_at -> t_sent` и полного `t_queued -> t_sent` по каждому тарифу (`pro`, `standart`, `base`);
  - доля `fast-skip`, пропущенные при догоне старые лоты, глубина очереди `outbox` и `RSS` процесса в МБ.
- **`/reload_proxies`** (только администратор) — атомарно перечитывает `proxies.txt` и `PROXY_URL` без перезапуска бота и без сброса `seen_items` или очереди доставки.
- **Офлайн-проверка и моделирование**:
  ```bash
  python -B tools/check_syntax.py
  python -B tools/run_offline_tests.py
  python -B tools/simulate_scheduler.py
  ```
